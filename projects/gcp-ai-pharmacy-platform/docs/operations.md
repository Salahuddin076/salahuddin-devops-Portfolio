# Operations

## Running the checks locally

```sh
cd projects/gcp-ai-pharmacy-platform

# Python static tests (stdlib unittest only, no network, no cloud calls)
python3 -m unittest discover -s tests -v

# Terraform formatting + per-directory validation
export TF_PLUGIN_CACHE_DIR=~/.terraform.d/plugin-cache
terraform fmt -check -recursive terraform
for d in terraform/modules/* terraform/examples/reference; do
  terraform -chdir="$d" init -backend=false -input=false
  terraform -chdir="$d" validate
done

# Helm
helm lint helm/pharmacy-service
helm lint helm/pharmacy-service -f helm/pharmacy-service/values-ai.yaml
helm template pharmacy-api helm/pharmacy-service --namespace pharmacy \
  | kubeconform -strict -summary
helm template pharmacy-ai helm/pharmacy-service -f helm/pharmacy-service/values-ai.yaml --namespace pharmacy \
  | kubeconform -strict -summary
```

`terraform plan`/`apply`/`destroy` are never run against this configuration — see the repository-wide `CLAUDE.md` rule. `terraform validate` is sufficient to catch provider-schema errors (wrong argument name, wrong type, missing required block) without needing real GCP credentials or a real project.

## Deploying the two workload releases (reference only — never actually run)

```sh
helm install pharmacy-api helm/pharmacy-service --namespace pharmacy
helm install pharmacy-ai helm/pharmacy-service -f helm/pharmacy-service/values-ai.yaml --namespace pharmacy
```

Each release is a separate Helm install because they target different node pools, different Google service accounts, and different resource shapes — not one chart with a loop over "workload types," since the two things that actually differ (scheduling and identity) are exactly the two things Helm's install-time values make easiest to keep straight as separate releases.

## Verifying a Workload Identity binding after a (hypothetical) deploy

```sh
kubectl get sa pharmacy-api -n pharmacy \
  -o jsonpath='{.metadata.annotations.iam\.gke\.io/gcp-service-account}'
# must equal the google_service_account.pharmacy_api.email Terraform created,
# and must match the google_service_account_iam_member binding's namespace/ksa_name.
```

## Rotating the Cloud SQL application password

The password is generated by Terraform (`random_password.app_user` in `modules/cloud-sql`) and never typed into a `.tfvars` file. To rotate it in a real deployment: `terraform taint` (or `-replace`) the `random_password` resource, apply, then re-apply the `secret-manager` module so the new value is written into the `db-credentials` Secret Manager version the API workload reads — in that order, so there's never a window where the live secret and the live database password disagree.

## Scale-to-zero behavior

The AI pool's `min_count = 0` means the GKE cluster autoscaler can remove every node in that pool when there are no unschedulable AI-tainted pods and no running ones. Nothing in this project automates "evenings and weekends only" scheduling (e.g., a CronJob that scales a Deployment's `replicas` to 0 outside working hours, which in turn lets the node-level autoscaler reclaim capacity) — the infrastructure supports it, but wiring a schedule is an application/platform-team decision left out of this reference's scope.
