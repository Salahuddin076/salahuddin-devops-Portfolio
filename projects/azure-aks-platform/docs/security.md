# Security

- **No local Kubernetes accounts.** `local_account_disabled = true` on `azurerm_kubernetes_cluster.this` (`terraform/modules/aks/main.tf`) means `az aks get-credentials` against this cluster can never fall back to a static client certificate or `clusterUser`/`clusterAdmin` credential -- every `kubectl` session authenticates as an Entra identity.
- **Azure RBAC for Kubernetes Authorization, not ClusterRoleBindings keyed to users.** `azure_active_directory_role_based_access_control { managed = true, azure_rbac_enabled = true }` makes Azure's own RBAC the authorization layer for the Kubernetes API, with `admin_group_object_ids` naming Entra *groups* (never individual users) as cluster-admins. Changing who has access is an Entra group membership change, not a Terraform apply.
- **No client secrets anywhere.** Grep this repo for `azuread_application_password` or `azuread_service_principal_password` and it returns nothing (`tests/test_terraform_static.py::test_no_client_secrets_or_connection_strings_anywhere`). Two separate federation patterns replace them:
  - **Pods**: `terraform/modules/workload-identity` creates one `azurerm_user_assigned_identity` + `azurerm_federated_identity_credential` per pod ServiceAccount, trusting the AKS cluster's own OIDC issuer for the exact subject `system:serviceaccount:<namespace>:<name>`.
  - **Azure DevOps pipelines**: `terraform/modules/pipeline-identity` creates an Entra app registration with a federated credential trusting `https://vstoken.dev.azure.com/<org>`, for the exact subject `sc://<org>/<project-id>/<service-connection-id>` that an Azure DevOps "workload identity federation" service connection presents. The pipeline identity is granted `AcrPush` only -- never `Owner`/`Contributor` on the subscription.
- **Key Vault as the only secret store, reached over RBAC, not access policies.** `enable_rbac_authorization = true` (`terraform/modules/platform/main.tf`) puts both control-plane (who can manage the vault) and data-plane (who can read secrets) authorization under one model. The AKS Key Vault Secrets Provider add-on's own identity gets `Key Vault Secrets User`; a pod's workload identity gets the same role scoped to the vault, granted from the example root once both identities exist (see `docs/decisions/0002-separate-state-per-root.md` for why that grant isn't inside either module).
- **No public network access on ACR or Key Vault.** Both set `public_network_access_enabled = false` and are reachable only through a private endpoint in the spoke's dedicated private-endpoints subnet, resolved by a private DNS zone linked to the spoke VNet (`privatelink.azurecr.io`, `privatelink.vaultcore.azure.net`).
- **Private AKS API server.** `private_cluster_enabled = true` and `private_cluster_public_fqdn_enabled = false`: there is no public DNS name for the API server at all, only a private one resolvable inside the peered VNets. Azure Bastion in the hub is the documented path for an operator to reach a node or jump box without a public IP or SSH NSG rule on anything in the spoke.
- **Egress is centrally filtered, not implicitly allowed.** The hub's `azurerm_firewall_policy` has an explicit `Allow` application-rule collection for the small set of FQDNs AKS genuinely needs (MCR, the AKS API, Entra login); everything else hits the policy's implicit deny. A spoke cannot route around the firewall: there is no NAT gateway, no public IP, no default-route-to-internet in the spoke at all.
- **Azure Policy add-on for baseline pod security.** `azure_policy_enabled = true` turns on Gatekeeper-backed policy enforcement; a real deployment assigns the built-in "Kubernetes cluster pod security baseline standards" initiative on top of this flag (the initiative assignment itself is an `azurerm_subscription_policy_assignment`/portal action against a real tenant, out of scope for a `terraform validate`-only reference, but the add-on that makes it possible is here and tested).
